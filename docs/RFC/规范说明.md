# RFC 正文本地留存

核注释里的规范引文用。本仓的注释大量引用 `RFC 9113 §6.5`、`RFC 6455 §4.1 第 8 条` 这类节号与序号，
每一条都是可核对的断言：那一节存不存在、说的是不是那件事。凭记忆核不出来，也不该拿网页摘要核——
实测同一个「这一节标题是什么、有没有步骤」的问题，两次摘要给出互相矛盾的答案。正文在这儿，
就能当场数。

## 集合从哪来

不手挑。集合就是仓库自己引用过的那些编号，从注释里推出来，所以引用一变、清单跟着变，
不会出现第二份需要人维护的名册：

```bash
# 在仓库根执行：把本仓引用到的 RFC 正文补齐到 docs/RFC/（已有的不重下）
git ls-files -z '*.h' '*.hpp' '*.cpp' '*.cc' '*.inl' '*.md' \
  | xargs -0 grep -ohE 'RFC [0-9]{4}' | awk '{print $2}' | sort -un \
  | while read -r n; do
      [ -s "docs/RFC/rfc${n}.txt" ] \
        || curl -sS -f -o "docs/RFC/rfc${n}.txt" "https://www.rfc-editor.org/rfc/rfc${n}.txt"
    done

ls docs/RFC/*.txt | wc -l        # 现在存了几份（每轮现数，别往文档里抄死）
du -sh docs/RFC                  # 体积
```

来源是 RFC Editor 的 `.txt` 原文，未做任何改写；文件名一律 `rfcNNNN.txt`。

## 核对引文的三条姿势

```bash
# 一：建「节号 → 标题」表。正文标题顶格，目录区的条目带缩进还有点线引导，
#      所以这个锚只会命中正文，不需要先剥目录
grep -nE '^[0-9]+(\.[0-9]+)*\.  +[A-Z]' docs/RFC/rfc6455.txt

# 二：取某一条编号条文的原文。列表项带前导空格，且「8.」后面的空格数不固定（实测是三格），
#      锚必须写成 ^ *8\.[[:space:]]+ 而不是 ^8\.——否则抓不到，还会误判「这一条不存在」。
#      两条本机实测的坑：必须带 -E（不带时是 BRE，`+` 退化成字面加号，静默零命中）；
#      别用 \s（GNU grep 的 -E 有 \b 与 \w，却没有 \s）
grep -nE -A8 '^ *8\.[[:space:]]+The request MUST include' docs/RFC/rfc6455.txt

# 三：看后继与取代关系（本仓同时引用了被取代的旧编号，那是刻意的历史引文）
grep -m1 -A2 '^Obsoletes:' docs/RFC/rfc9110.txt
```

判一条引文对不对，两问都要过：这一节存不存在；那一节写的是不是注释声称的那件事。
第二问更容易失手——节号确实存在、但讲的是隔壁那件事，这种注释比没写更误导。

## 为什么不入库

`.gitignore` 里挡掉的是 `docs/RFC/*.txt`，本文件照常跟踪。两条理由：

- 体积。整集合是若干 MB 的外部文档，而它随时能按上面那条循环重生成，没有「丢了就没了」的问题。
- 扫描面。RFC 正文自带示例凭据与密钥向量（`RFC 6750` 的 `access_token`、`RFC 9001` 附录 A 的密钥、
  `RFC 7519` 的 JWT 样例）。供应链作业用 `gitleaks dir` 扫的是 checkout 出来的工作树，
  也就是跟踪文件；不入库就凭空多出几十片需要写豁免面的地方。

需要某一份而本地没有，跑一遍上面那条循环即可。
