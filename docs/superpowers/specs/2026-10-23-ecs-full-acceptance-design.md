# 远端 ECS 全能力与性能验收设计

- 日期：2026-10-23
- 状态：待用户评审
- 对象：`develop` 当前 HEAD 的 AsynGyanis 1.0.0（执行时钉死提交号）
- 决策：能力清单驱动；单台 2C2G Linux ECS；本机容器构建上传；重资源门禁留在本机；可判定项修复到绿

## 1. 背景与目标

本轮要在远端 ECS 上验证引擎的全部已声称能力与性能，并在发现可判定缺陷时修复到绿。此前任何 ECS 验收台账、结论、脚本与“已知问题”清单都不作为本轮输入；能力清单、判据与证据全部从当前仓库的 README、docs、公开头文件与现有测试资产重新生成。

目标：

1. 给出一张可审计的能力矩阵，覆盖 Platform、Base、Core、Net、Database 五个模块的已声称能力。
2. 在 ECS 上以真实进程、真实套接字和真实协议路径完成运行时验收，不以进程内桩代替。
3. 在本机补齐 ECS 不适合承担的重资源门禁：真实数据库、Docker 类裁判、ASan、TSan、模糊。
4. 给出五类可压协议的容量曲线、饱和点、长稳漂移、功能开销对与 ECS 本机基线。
5. 把矩阵中的 `red` 与 `gap` 清零；`n-a` 必须带原因与补验条件，不能冒充绿。

## 2. 非目标

- 不在 ECS 上验证 Windows 专属实现（IOCP、Windows 文件监视、Windows 服务通知等）；这些只在 `local-windows` 冒烟并标注平台归属。
- 不把 2C2G 的吞吐或分位外推为生产容量或与其它引擎比较。
- 不为未声称的新能力扩围；若修复需要新增能力或改架构，按第 7 节的升级规则停下来由用户决策。
- 不在没有公网域名与 DNS 凭据时声称完成真实 ACME 签发；没有条件时标 `n-a` 并写补验条件。
- 不把历史轮次的用例条数、覆盖率、模糊执行数或性能数字当成本轮证据。

## 3. 机器分工与产物

### 3.1 机器角色

| 角色 | 机器 | 承担 | 不承担 |
| --- | --- | --- | --- |
| `ecs` | 单台 Linux 2C2G | Release 全量 ctest 分片、Linux 示例、ReferenceServer 全部部署形态、协议与部署验收、h2spec/aioquic/ws_interop、同机与跨机容量测量 | Debug/ASan/TSan、模糊、Docker 类裁判、MySQL/PostgreSQL/Redis 真机 |
| `local-linux` | 本机 Docker 内的 Linux 容器 | 按 ECS 发行版与 glibc 匹配的构建；Debug+ASan、TSan、模糊；四类数据库真机与 TLS 变体；Autobahn、Pebble | 代表 ECS 的运行时结论 |
| `local-windows` | 本机 Windows | 跨公网发压客户端；Windows 专属能力冒烟 | ECS 的绿 |

### 3.2 构建与上传

1. `local-linux` 先采集 ECS 的发行版、glibc、架构，用匹配镜像构建 Release 包：GCC、`-O3 -DNDEBUG`、mimalloc ON、加固 ON、不开全程序优化。
2. 包内包含：库与运行时依赖、`ReferenceServer`、13 个示例、Release 测试二进制、夹具证书、微基准、压测脚本、`SHA256SUMS`。
3. 动态依赖随包携带，启动脚本显式设置库搜索路径；上传后在 ECS 用 `ldd` 证明全部解析。
4. 包内不含真实凭据、账户材料或私钥；测试证书只使用仓库夹具或现场生成的一次性自签证书。
5. ECS 不在机上编译；修复后的每次重传都带新的提交号与哈希。

### 3.3 Phase 0 预检

任何“绿”结论之前先采集并记录：

- 发行版、内核、glibc、CPU 架构、逻辑核数；
- 内存、swap、磁盘余量、inode 余量；
- `ulimit -n`、可用临时端口范围、IPv4/IPv6 状态；
- systemd 是否存在且可管理服务、cgroup v2 是否可读；
- `io_uring_setup` 是否被 seccomp 或内核策略放行；
- 上传包哈希校验、`ldd` 全解析、动态库可加载；
- 一次启动、请求、优雅停止冒烟。

任一项不满足，先修打包或把相关能力标 `n-a`，不带病进入矩阵。

## 4. 能力矩阵

### 4.1 单一真源

矩阵落在 `tests/acceptance/capabilities.yaml`，是全轮唯一的判决来源。最终报告由矩阵导出，不手写结论。

每行字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定标识，形如 `NET.HTTP2.MULTIPLEX` |
| `module` | Platform / Base / Core / Net / Database |
| `capability` | 一句话能力描述 |
| `claim_source` | README 段落、docs 标题或公开头文件路径 |
| `platform` | linux / windows / posix / any |
| `runner` | ecs / local-linux / local-windows |
| `prerequisites` | 服务、环境变量、端口、证书、内核开关 |
| `entry` | 测试过滤、示例名、脚本或探针 |
| `command` | 可直接执行的一条命令 |
| `oracle` | 通过判据，必须能判真假 |
| `evidence` | 证据路径模板 |
| `status` | unverified / green / red / gap / n-a / blocked |
| `defect` | 缺陷编号，可为空 |
| `regression_test` | 回归用例标识，可为空 |

### 4.2 完整性论证

从四个方向对账，任何一条声称都必须落到矩阵行：

1. README「核心特性」五段逐句拆条；
2. `docs/` 七章的能力小节逐条拆；
3. `packaging/api-baseline.txt` 与 `scripts/report-public-surface.py` 的公开符号逐个归类到能力行，或明确标为内部/不适用；
4. 现有 `tests/`、`samples/`、`scripts/` 反向映射到能力行；没有任何行引用的资产要么补行，要么标为冗余待清。

矩阵之外不允许存在“口头已知”的能力。找不到 runner 的声称一律落成 `gap`。

### 4.3 状态与分类

| 状态/分类 | 含义 | 处置 |
| --- | --- | --- |
| `green` | 本轮命令已执行，oracle 成立，证据落盘 | 保持，最终全量复跑 |
| `red-product` | 引擎行为与声称/规范不符 | 修复并补回归 |
| `red-harness` | 测试、脚本、夹具或打包缺陷 | 修复并自证判据可红可绿 |
| `gap` | 有声称但无裁判或公开面未被驱动 | 补探针，或按证据改声称 |
| `n-a` | 平台、环境或上游条件不可能 | 写原因与补验条件，不算绿 |
| `blocked` | 依赖外部状态暂时不可用 | 写阻塞点、已耗时与恢复条件；不能长期停留 |

`n-a` 只允许三类：平台专属、环境缺失（无公网域名、无 Docker、内核不放行等）、上游不可用（真机构配额、第三方服务）。每条 `n-a` 必须写“在什么条件下由哪个 runner 补验”。

### 4.4 已限定的声称

以下各项在源码或 docs 中已是显式设计决定或已限定范围，不按“缺失能力”处理；矩阵仍要为它们建立证据行，证明实际行为与限定一致：

| 项 | 限定内容 | 矩阵处置 |
| --- | --- | --- |
| HTTP/2 流优先级 | 不建优先级树，PRIORITY 收下即弃（RFC 9113 允许）；未声称 RFC 9218 调度 | 帧处理与拒错为 green；QoS 调度标 `n-a` |
| PROXY 协议 | 仅 TCP 入站 v1/v2 读侧；未声称 QUIC/h3 的 PROXY 头 | TCP 行为为 green；QUIC PROXY 标 `n-a` |
| 多进程指标 | 每进程监听 `metrics_port + 序号`，由采集端按进程抓取；不提供单端点聚合 | 按进程抓取为 green；单端点聚合标 `n-a` |
| ReferenceServer 的 HTTP-01 | 开了 HTTPS 就没有明文口，启动被拒并指回 DNS-01；首次签发归探针 | 启动拒绝与提示为 green；服务侧 HTTP-01 标 `n-a` |
| h3 示例的真实请求 | 示例只验配置、畸形报文、定时与排空；真实握手与请求由单测与 aioquic 覆盖 | 示例行为为 green；真实 h3 请求由 W2 裁判为 green |
| io_uring | 编译期选择后端，不做运行期切换；seccomp 不放行时跳过运行 | 编译档与放行时运行为 green；运行期切换标 `n-a` |
| 热重载范围 | 仅 logging 段与 h1/h2 连接限额；路由、监听地址、线程数、metrics_port、运维令牌启动期定型 | 已实现范围为 green；范围外标 `n-a` |

## 5. 执行波次

| 波次 | 范围 | 主入口 | 主要裁判 |
| --- | --- | --- | --- |
| W0 预检 | 机器事实、包完整性、启动停止 | Phase 0 清单 | ECS 现场读数 |
| W1 平台/基础/运行时 | Platform 原语、配置/日志/异常、事件循环、协程/取消/线程池、TLS/mTLS、进程编排 | Release ctest 分片；`BaseLog`、`BaseConfig`、`PlatformPrimitives`、`CoreLoop`、`CoreTls`、`CoreWorker` | gtest + 示例自检 |
| W2 协议面 | h1、h2c、h2+TLS、h3/QUIC、WS、出站客户端、PROXY v1/v2、UDP | Release ctest；`NetHttpDemo`、`NetHttpsH2Demo`、`NetHttp3Demo`、`NetUdpDemo`、`NetGateway` | h2spec（h2c/TLS）、aioquic（h3/QUIC/取消）、ws_interop、Autobahn（本机） |
| W3 部署形态 | ReferenceServer 全部开关、多进程 worker、崩溃补位、SIGHUP、零停机换代、systemd 就绪/看门狗、CPU 亲和、静态与运维端点 | 进程外驱动；`CoreUpgrade`、`NetGateway` | 外部客户端 + 进程/端口观测 |
| W4 数据访问 | SQLite、池、事务/保存点、流式结果、ORM/方言/迁移；MySQL/PostgreSQL/Redis/Sentinel 真机与 TLS 变体 | ECS 跑 SQLite 与无依赖用例；本机容器跑真机 | gtest + 真实服务 |
| W5 安全与证书 | TLS 策略、会话票据、热轮换、mTLS、安全头、ACME 装配与续期、HTTP-01 探针、DNS-01 写侧 | ECS TLS/mTLS/轮换；本机 Pebble | Pebble、staging 机构、探针 |
| W6 配置与可观测性 | YAML/JSON 装载与热重载范围、四类日志 sink、Prometheus/healthz/readyz/debug、OTLP 指标与日志、追踪、进程指标注册表 | ECS 端到端抓取；本机独立 collector 对收 | 端点读数 + collector |
| W7 判定复核 | 修复后的受影响波次复跑，再一次全矩阵复跑 | W1–W6 的同一入口 | 同一提交号与同一包哈希 |

W2/W3 的 h3、零停机与多进程必须走真实 UDP/TCP 与真实进程，不使用进程内桩。

### 5.1 每波的记录

每一波产生一份原始日志目录，包含：命令、开始/结束时间、退出码、stdout/stderr、失败用例列表、服务端进程与端口状态、资源峰值。`ctest` 只在失败时保留用例输出，因此每波结束要立即复制当轮日志，不能依赖事后回看。

## 6. 性能测量

### 6.1 负载矩阵

| 负载 | 服务形状 | 客户端 | 并发点 |
| --- | --- | --- | --- |
| h1 keep-alive | `/bench` 小响应、`/big` 大响应、静态文件 | `wrk`（同机与跨机） | 1/8/32/64 |
| h1 短连接 churn | 每连接一请求即关 | `soak.py` 的 churn 形状 | 8 线程 × 1/8/32/64 |
| h2c / h2+TLS | 单连接多流、`/bench` | `h2load` | 1/4/16 连接 × 32/64 流 |
| h3 / QUIC | `/bench`、`/big` | 仓库内 C++ h3 客户端作容量客户端；aioquic 只作一致性裁判 | 1/4/16 连接 |
| WebSocket | 回显与 Hub 扇出 | 优先现有 C++ 客户端；没有则在 `tests/Tools/` 补负载探针，Python 只作交叉核对 | 1/8/32/64 连接 |
| 功能开销对 | TLS 开/关、压缩开/关、指标端点开/关、追踪开/关、静态 vs 动态 | 与基线同客户端、同并发 | 各自饱和点前一档 |

`wrk`、`h2load`、`aioquic`、Autobahn、Pebble 与 Python 依赖都按固定版本安装或随包携带，并在报告中记录版本与来源；版本不可核对时不采用其读数。

### 6.2 测量协议

- 每点预热 10 s、测量 30 s、冷却 5 s，三轮取中位。
- 记录吞吐、p50/p95/p99/max、失败分类、CPU user/sys、RSS 峰值、fd 峰值、网卡收发字节、服务端请求计数。
- 客户端 CPU 超过 80% 或链路利用率超过 70% 时，该点标 `client-bound` 或 `link-bound`，不作为引擎上限。
- 同机回环与跨机两套读数分开成表，绝不互比。
- 所有读数带提交号、构建旗标、ulimit、CPU 型号、后台负载与客户端位置。

### 6.3 饱和点

并发翻倍后吞吐增幅小于 5%，且 p99 劣化超过 2× 或开始出现错误，即判到达饱和。报告同时给出最紧的资源（CPU、fd、网络、内存）作为瓶颈证据。容量曲线只画到最后一个未饱和点，并单列饱和点。

### 6.4 长稳与资源漂移

h1 keep-alive、h1 churn、h2c、h3、WS 各跑 30–60 分钟。判绿条件：

- 零请求失败、零意外 GOAWAY/RST；
- 静默后 fd 回到基线 +4/循环以内；
- RSS 在预热 10 分钟后按 10 秒采样，后 20 分钟线性斜率不超过预热值的 0.5%/小时，且末值不超过预热值 110%。

任一条不满足先复跑一次；仍复现才判 `red-product`，并附分配器统计与服务端计数。

### 6.5 功能开销对

对 TLS、压缩、指标端点、追踪、静态文件各做开/关成对测量，使用同一客户端、同一并发点、同一持续时间。报告比值与三轮范围，只做同机相对比较，不跨机比绝对值。

### 6.6 ECS 本机回归基线

在 ECS 上重录 Release 基线：微基准三轮取中位、各协议容量点、soak 形状。基线文件带机器指纹与运行条件。后续同机复跑按吞吐 0.6×、p50 1.5×、p95 2.0×、p99 2.5× 判回归；`n-a` 与 `client-bound` 点不参与判定。

### 6.7 边界

- 2C2G 上客户端与服务同机时，读数是“共同上限”，不是引擎单独能力。
- h3 与 WS 若客户端先饱和，报告明确写“下限”，并用跨机 C++ 客户端补一轮。
- 数据访问性能只做本机微基准与真机连通性，不在 ECS 上做数据库容量曲线。
- 任何性能结论缺提交号、构建选项、机器条件或客户端位置时，不作为本轮证据。

## 7. 修复闭环

### 7.1 分支与提交

从 `develop` 切 `acceptance/ecs-1.0.0`。修复与新用例只进该分支，不直接改 `develop`，不自动推送。每个缺陷一笔提交，正文写复现、根因、修复与回归；提交范围用模块名，不用发现编号。

### 7.2 缺陷记录

每条 `red` 或 `gap` 建立台账记录：症状、最小复现、根因、分类、修复提交、回归测试、修复前后证据。回归用例必须先证明“改回旧实现会红”，再证明修复后绿。

### 7.3 重建与复验

修复后重建 Release 包、校验哈希、重传 ECS；先重跑受影响波次，再在最终提交号上跑一次全矩阵。最终报告只引用最终提交号与最终包哈希的读数。

### 7.4 升级规则

若修复需要新增未被声称的能力、改动架构或引入新的外部依赖，停下并给出三个选项：补实现、改声称、标 `n-a`；由用户决定后再继续。不得自行扩围。

### 7.5 安全与清理

- ECS 只在测试期开放必要端口，结束后关闭安全组规则。
- 不把口令、令牌、账户材料或私钥写进仓库、日志与报告；诊断中的 URL 凭据必须脱敏。
- 测试结束停止所有被测进程与外部裁判，删除临时证书与一次性账户材料，保留报告与必要原始日志。
- 上传包与报告都带校验和；报告目录与仓库分离。

## 9. 风险与处置

| 风险 | 处置 |
| --- | --- |
| 构建容器与 ECS 的 glibc/发行版不匹配 | Phase 0 先验；按 ECS 匹配镜像重建；不匹配即停 |
| 2C2G 内存不足导致 OOM | ECS 只跑 Release；ctest 串行分片；必要时加 swap；记录 OOM 现场 |
| 公网压测暴露服务 | 临时安全组；仅测试期监听；无真实凭据；结束后关闭 |
| 公网链路抖动主导读数 | 同机与跨机双读数；记录 RTT 与带宽；标注链路受限 |
| h3/WS 客户端先饱和 | 优先 C++ 客户端；记录客户端 CPU；报告写“下限”并补跨机轮次 |
| 外部裁判不可用 | 本机容器补位；仍不可用标 `blocked`，写阻塞点与恢复条件 |
| 修复扩围失控 | 按第 7.4 节升级规则停下来由用户决策 |
| 历史记忆污染 | 本轮不读取旧 ECS 台账/结论；矩阵从当前仓库重新生成 |

## 10. 完成判据

1. 矩阵中不存在 `unverified`、`red`、`gap`、`blocked`，只剩 `green` 与有理由的 `n-a`。
2. 每条 green 都有命令、判据与证据路径；每条 n-a 都有原因与补验条件。
3. 所有修复在最终提交号上通过一次全矩阵复跑，并同时通过本机 Debug+ASan 与 ECS Release 全量 ctest、示例矩阵、格式与静态门禁。
4. 性能四类产物齐全：容量曲线与饱和点、长稳与漂移、功能开销对、ECS 基线；客户端与链路受限点已标注。
5. 报告、原始证据、基线、上传包哈希齐全；ECS 临时进程、端口与安全组规则已清理。

## 11. 验收器自检

- 矩阵每行必须能解析到存在的入口与命令；缺失入口直接判 `gap`，不静默跳过。
- `run_acceptance.py` 提供 dry-run，列出将执行的命令、依赖与证据路径，不启动服务。
- 每个新增或改动的 oracle 必须能证伪：用一个人为突变或已知失败证明它会红，再证明修复后转绿；既有 green 项至少抽取一条做同样的反向对照，证明判据没有空转。
- 证据完整性检查：每条 green 的日志、退出码、判据读数必须同时存在；缺一即降级为 `unverified`。
- 密钥扫描：上传包、日志与报告中不得出现真实凭据；扫描命中即阻断交付。

## 12. 输入与假设

- ECS 的发行版、内核、glibc 与资源上限在 Phase 0 采集；未采集前不定义具体镜像标签。
