# 性能测试

[返回文档导航](文档导航.md)

本文说明两类测量各自的口径、怎么复现、以及哪些结论**不能**从它们得出。功能验证面见 [测试与验证](测试与验证.md)。

## 两类测量，两套基线

| 类别 | 入口 | 基线 | 是否在 CI |
| --- | --- | --- | --- |
| 热路径微基准 | `benchmarks/run-microbench.bat`、构建目标 `microbench` | `benchmarks/microbench-baseline.json` | 是（Windows 的 `微基准读数（三跑取中位，只报不断）`） |
| 进程外压测（soak） | `benchmarks/run-soak.bat`（Windows）、`benchmarks/run-soak.sh`（Linux） | `benchmarks/baseline.json` / `benchmarks/baseline-linux.json` | 否 |

soak 不进 CI 的理由是具体的：那是分钟级的长负载，一轮就要占掉整条作业的预算，而同机压测会把 runner 自己变成噪声源。微基准进 CI 但**只报不断**——共享 runner 的波动幅度还没攒够几轮真实读数，先设阈值只会制造假红；比对时显式传 `--minimum-throughput-ratio 0`，把判定线留到数据够多之后再抬。

## 复现

微基准（Release 档；读数只在 Release 有意义）：

```bash
cmake --preset release
cmake --build build/release --target microbench
./build/release/benchmarks/microbench/microbench.exe --json-out run.json
python benchmarks/check-baseline.py --baseline benchmarks/microbench-baseline.json run.json
```

三跑取中位是 CI 那一步的口径（`--json-out` 三份一起交给 `check-baseline.py`）。本地单次跑只能看方向，不能当基线。

进程外压测：

```bat
cmake --build build/release --target ReferenceServer
set ASYN_SOAK_BUILD=release && benchmarks\run-soak.bat
```

Linux 侧走 `benchmarks/run-soak.sh`，比对它自己的 `benchmarks/baseline-linux.json`。

## 门禁判什么

`benchmarks/check-baseline.py` 的回归线：吞吐劣化超过 `0.60×`、p50 劣于 `1.50×`、p95 劣于 `2.00×`、p99 劣于 `2.50×` 判回归。`maximum` 只录不判——单次调度抖动就能让它翻倍。基线里缺哪一档判据会当场报红而不是静默跳过：「测量脚本已经产出 p99、门禁还只判 p50/p95」这种两头各写一份的漂移就是这么堵住的。

## 口径与边界

- **只能同机前后对比**。换一次会话、换个邻居负载都能差出近一倍，跨机器比没有意义，因此这里不写「比谁快」的结论。同一份代码在容器里的 keepalive p50 与宿主差着四五倍，差的是虚拟机回路与宿主后台状态，不是代码——两份基线**绝不互比**。
- 单进程、同机回环，客户端与被测服务共享同一台机器。
- **短连接 churn 一路是发压端封顶**：客户端是 8 条阻塞式线程、每条连接只发一条请求就关，p95/p99 又受本机临时端口与 2MSL/TIME_WAIT 支配。它只够确认 accept/close 通路没有成片失败，不能从吞吐或分位推断这条路径有没有退化。
- 保持连接那一路的 p50 主要不是单次服务耗时而是排队延迟（并发连接数压在工作线程数上，客户端自身也是瓶颈之一），所以它适合看前后变化，不适合当单次请求延迟的绝对值。
- ASan 构建下的长期内存曲线渐近饱和是 quarantine 而不是泄漏；判泄漏要用 `quarantine_size_mb=1` 之类的对照重跑。

## 构建配置对性能的影响

`release` 预设关闭 sanitizer、启用优化，并保留能解析调用栈的调试信息。两个默认关闭的开关各有明确理由，不是没来得及打开：

- **`ASYN_WITH_MIMALLOC`**：默认 **ON**（生产/Release 构建走 mimalloc），与 sanitizer **互斥**（会遮蔽 ASan/LSan/TSan 的分配拦截，配置阶段直接 `FATAL_ERROR`）。因此 debug 预设、TSan 档与覆盖率档都显式传 `-DASYN_WITH_MIMALLOC=OFF`——内存与线程门禁仍按原样跑，只是不用替身分配器。接管是全局的（`Core` 以 PUBLIC 链入 `mimalloc-static`，最终可执行文件的 `malloc/free` 整个换掉），包消费方要能在 Conan 缓存里找到它；共享形态（`BUILD_SHARED_LIBS=ON`）下静态分配器只进 `Core` 那个 DLL，不做进程级替换。
- **`ASYN_WITH_IO_URING`**：容器与部分宿主内核的 seccomp 会挡 `io_uring_setup`（`EPERM`），默认打开会让「在这台机器上建不起事件循环」成为常态失败；而且它只改后端选择（`Epoll.h` 里 `using Epoll = Uring`），三后端共用一套契约、多数断言在 epoll 下恒绿，所以对齐靠 CI 里那条 `io_uring 的编译档` 作业**带着用例**跑出来（内核不放行时跳过运行，不放行就等于没测）。
- **不做全程序优化（`/GL` + `/LTCG`）**：`f37d3035` 实地对照过——hpack-decode 快 12.6%、http2-frame-decode 快 14.9%、http-date-format 快 17.3%，而 http1-parse-request 反慢 3.5%、hpack-encode 慢 0.6%，收益是散的；而且 `/GL` 编出的静态库是 CGALLIB（同批实测 `Net.lib` 达 232 MB），非 `/LTCG` 的消费者链不动它，而本仓对外交付的恰恰是静态库与 Conan 包。这一档的口径记在 `benchmarks/microbench-baseline.json` 的 `build` 字段。没测过的收益不写，测过但划不来的也不开。
- **`ASYN_ENABLE_HARDENING` 默认开**：它是部署形态该有的底色，关掉才需要理由。加固项（栈保护、`_FORTIFY_SOURCE`、RELRO/NOW、`/guard:cf`）对吞吐的影响包含在上面那两份基线里——换基线前先确认两档的加固设置一致。

## 留档读数

下表是 2026-09-24 的一次实测留档，**不是当前基线**：当前读数从当次运行或基线文件取。

测量条件：`ReferenceServer` Release（MSVC `/O2`、不开全程序优化、无插桩、加固默认开），`--threads 4`，单进程同机回环，三轮取中位。

| 场景 | 中位吞吐 | 三轮范围 | p50 | p95 |
| --- | --- | --- | --- | --- |
| HTTP/1.1 保持连接（8 线程 × 8 连接） | 54,804 请求/s | 49,106 ~ 55,232 | 131.9 µs | 234.1 µs |
| HTTP/1.1 短连接 churn | 2,646 连接/s | 2,493 ~ 2,657 | 363.3 µs | 14.9 ms |

三轮合计 38,400 条保持连接请求与 12,000 条短连接，失败 0；服务端句柄数 184 → 收尾 220~253（峰值 384），工作集 10.4 → 13.0 MiB 上下，跑完不漂移。

测量硬件：Intel i5-14600KF（20 逻辑核）、32 GB 内存、Windows 11（10.0.26200）、NVMe；Linux 那一档在同一台机器的 ubuntu24 容器里录（GCC 13.3，`-O3 -DNDEBUG`，不带插桩）。

## 改动前后怎么比

1. 在同一台机器、同一构建目录形态下各跑一次（改前 / 改后），别混用 Debug 与 Release、别混用带与不带 sanitizer 的档。
2. 微基准三跑取中位再比对；soak 用 `check-baseline.py` 对它自己那一份基线。
3. 想看「还有哪些代码没被触达」是覆盖率问题，不是性能问题，见 [测试与验证](测试与验证.md)。
4. 结论写进 PR 或提交正文时带上日期、硬件、构建选项与适用边界；缺这些的读数对下一个人没有可比性。
